# ADR-008：macOS API Secret 的会话轮换边界

## 状态

已接受

## 日期

2026-07-27

## 背景

ADR-001 在当前 ad-hoc 签名约束下选择权限受限的 `.api-secret`，并明确拒绝现在迁移
Keychain。需要进一步判断：是否应在每次连接时生成新的 Mihomo API secret，以缩短旧
secret 的有效期。

macOS 当前有三类启动路径：普通系统代理连接、授权后的 TUN 连接、健康检查触发的自动
恢复。它们都必须让设置内存、原子生成的运行配置、Mihomo API 客户端和恢复事务观察到
同一个 secret。运行中的 `config.yaml` 或 TUN 暂存配置仍必须包含明文 secret。

## 决策

1. 4.0.0 不启用“每次点击连接即轮换”，也不迁移 Keychain。
2. 会话轮换在技术上可行，但只能发生在“当前没有任何普通或特权核心、没有待恢复连接、
   没有启动/停止事务”的连接边界。轮换必须作为一个完整事务完成：
   - 生成高熵候选值；
   - 写入 `.api-secret` 并回读逐字验证；
   - 用同一值生成并原子提交运行配置；
   - 将不可变设置快照交给普通启动、TUN 启动和自动恢复；
   - 任一步骤失败时，恢复并验证上一值，且不得启动核心。
3. 自动恢复和同一连接的核心重启必须复用该会话值，不能再次轮换。否则恢复计划、TUN
   暂存配置与 API 健康检查会产生代际分裂。
4. 在实现会话轮换前，必须先引入跨普通/TUN/恢复路径共享的 `sessionGeneration` 与
   secret 快照契约，并添加以下故障注入测试：
   - secret 写入或回读失败；
   - 配置原子提交失败；
   - 轮换后启动失败；
   - 旧自动恢复任务晚到；
   - TUN 授权返回晚于取消；
   - 应用崩溃发生在 secret 提交与配置提交之间。
5. 当前继续沿用 ADR-001 的长期 secret，并在显式重置时轮换。诊断历史、日志和错误信息
   仍不得包含 secret。

## 理由

- 单纯在 `start()` 内生成新值会破坏配置生成先于启动的现有边界，也会让自动恢复捕获的
  设置快照失效。
- 每次连接写入 `.api-secret` 会增加新的双文件提交窗口；没有 session generation 时，
  崩溃后无法可靠判断 secret 与运行配置属于哪个会话。
- 对已获得同一 macOS 用户权限的恶意进程，轮换收益有限：它仍可读取当前运行配置或访问
  当前回环 API。轮换减少的是旧副本的有效期，不是同用户进程边界。
- Keychain 仍受 ADR-001 所述 ad-hoc 签名身份不稳定约束；会话轮换不能替代稳定签名，
  也不需要为了轮换先迁移 Keychain。

## 后果

- 4.0.0 不引入会导致恢复链路失配的半成品轮换。
- `.api-secret` 仍是需要保护的长期文件，运行配置仍是会话期敏感文件。
- 后续可以在显式 session generation 契约落地后，以新的实现 ADR 取代本决策的“暂不
  启用”部分，而无需改变 Keychain 结论。

## 未采用的方案

### 每次调用 `start()` 都直接轮换

启动调用可能来自用户连接、自动恢复或并发重试，无法代表一个新会话；该方案会使晚到的
恢复任务持有旧 secret，因此拒绝。

### 只轮换内存和运行配置，不更新 `.api-secret`

应用崩溃或重启后无法恢复当前控制凭据，且长期存储与运行配置会立即分叉，因此拒绝。

### 现在迁移 Keychain

不解决会话代际和多启动路径的一致性问题，并重新引入 ADR-001 已记录的 ad-hoc 签名升级
风险，因此不在本次范围内。
