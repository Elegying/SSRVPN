# ADR-018：规则优先的双栈分流与代理内地址选择

状态：2026-09-18 定稿，已随 5.0.12 实装（核心与 DNS 开启 IPv6、三端 TUN 接管 IPv6），取代 ADR-016 的 IPv4-only 边界；
Windows IPv4-only 网络、节点真实 IPv6 出口与 UDP/QUIC 采样仍待覆盖。

## 行为

智能模式下，IPv4 和 IPv6 使用同一套应用、用户、域名、企业网络、GeoIP 与兜底规则。
国内目标直连，需代理及未知目标经选中节点。全局模式继续遵守已有全局语义，
用户手动规则及 Android 应用优先级不变。IPv6 不再在所有用户规则之前一律拒绝。

核心和 DNS 开启 IPv6，三端 TUN 显式接管 IPv6。接管地址不依赖客户端当前是否有
公网 IPv6，因为节点可通过 IPv4 隧道提供 IPv6 出口。不修改操作系统 IPv6 开关。

共享核心扩展只在规则选定出口后选择目标地址，不以 IPv4/IPv6 决定 DIRECT/PROXY。
SS/SSR/Trojan/VMess/VLESS/Hysteria/Hysteria2/TUIC/AnyTLS 的 TCP 保留目标域名给已选节点
解析，避免把无可靠目标确认的协议固定到本机优先地址后，再因首写失败重放应用请求。
显式 hosts、内部 DNS 和没有可恢复域名的字面地址保持原义。

其他代理复用原有解析器、缓存和 DNS 分流，最多四个去重 IPv4、四个 IPv6，交错尝试，
最后保留原域名解析。实际收到响应数据才记录节点+目标+传输协议的短期地址族偏好，
不从拨号成功推导节点能力。缓存最多 256 条、60 秒，不作阻塞式外部能力探测。
地址尝试仍受原连接总预算与有限重试约束；解析最多两秒。一次拨号耗尽预算时仍可能
来不及尝试另一族，这是待继续验证的限制，不延长总等待、不改成 DIRECT。
应用数据一旦交给协议写入，即使返回错误，也不得重放至另一地址。

DNS 同时配置 IPv4/IPv6 Fake-IP 池，与虚拟接口地址分离；通用 DNS、直连 DNS、节点入口
DNS 的策略保持分工。收到一族有效结果后仅短暂等待另一族，避免单族超时拖住可用族。
订阅安全解析识别精确 Fake-IP 范围，不豁免任意私网或 ULA。

这不是 NAT64。IPv6-only 目标通过原节点尝试 IPv6，不假装能转换为 IPv4，
不依据节点服务器地址判断节点的 IPv6 出口能力，不自动换节点或断开整体 VPN。
HTTPS 的 TLS/SNI/HTTP Host 字节不改，变更仅作用于代理协议承载的目标地址。

## 诊断和边界

最终拨号失败且确实尝试过 IPv6 目标时，核心输出固定事件，不含目标或凭据。
认证的 `/ssrvpn/traffic` 增加会话内失败计数和距最近失败的毫秒数；
手动诊断只展示最近一分钟内的失败观察，三端复用同一中文说明。
旧会话迟到结果不写入新会话。失败表示网络、节点或目标的该次访问未成功，
不能证明节点永久不支持 IPv6。旧核心缺字段时不误报。

部分代理协议的 TCP/UDP 不返回远端连接确认，拨号成功不能保证应用层可用。
Hysteria2 等协议可能在首次读取时才返回远端目标连接结果，届时拨号重试已经结束。
现有 IPv6 失败计数仅覆盖最终拨号失败，不是完整的应用层失败统计；计数为零不能证明
IPv6 访问正常。不得为地址回退重放已经发送的应用请求，也不得将代理失败降级为直连。
UDP 无响应尤其不能单独证明 IPv6 能力；不作确定性归因。
本地没有 IPv6 出口的环境无法直连 IPv6-only 国内目标，双栈目标依赖正常 IPv4 回退。
此候选不能代替 Windows TUN、防火墙、真实节点和移动网络的实机验证。

## DIRECT 地址族兼容（待实机验证）

三端共用补试逻辑：仅首次 DIRECT TCP 拨号失败、应用数据尚未发送、有可恢复域名时，
使用原直连解析器在总预算内尝试一个相反地址族。保留接口绑定、回环检查与取消，
不更换 DIRECT 策略；内部请求、显式 hosts、无域名地址不参与。无另一族时如实失败。
Windows 用户报告中的 `bind6` 是此路径的具体已观察案例，不能据此认定所有抖音故障相同。

2026-09-18 增量：DIRECT 的真实 IPv6 DNSMapping 保留可信恢复域名，避免 `Pure()`
提前固定 AAAA，交由原生 TCP 双栈竞争及 UDP 地址解析。显式 hosts、内部请求、
无域名地址和仅有嗅探域名的目标不扩大改写范围。物理出口明确仅有 IPv4 源地址时，
DIRECT 先完成 A 查询，防止先返回的 AAAA 部分结果掩盖较慢的 A；不修改应用收到的
AAAA、PROXY 解析或 TUN 捕获配置。复用核心接口缓存及网络监控，不进行阻塞外部探测。
GUA/ULA 存在并不证明 Internet 可用，默认路由及实际外网能力的完整认证仍未实现；
不会在诊断中虚报可用。既有 UDP 会话不重放，真实切网/睡眠与 QUIC 仍需平台验收。

## 接管生命周期与例外

维护者确认保留 Android 国内应用系统排除名单：这些应用双栈均不进入 VPN，网站规则
不能覆盖它们。系统代理不保证接管不遵守代理的应用。
仅打开应用不主动建立新连接；断开、核心退出和真正退出应恢复网络，不添加 kill switch。
关闭窗口仍驻留托盘与真正退出不同，外部探测失败与核心退出不同。
维护者确认采用准备/提交两阶段：加载核心和规则不接管，最后提交 TUN 并立即验证，
失败或取消恢复网络。三端固定核心把 TUN 创建放在 provider 初始化之后，并在必需
SSRVPN provider 为空时拒绝接管。macOS runner 等待固定提交标记后才修改 DNS。
Android 先以无 TUN 模式准备核心，确认规则与节点选择后再建立 VPN 并交付描述符；
准备和提交共用原有总超时预算。该实现仍需实际安装后的路由、取消和异常退出验收。
