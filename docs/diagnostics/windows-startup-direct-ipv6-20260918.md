# Windows 启动等待与直连 IPv6 失败排查（2026-09-18）

## 用户 A：首次失败，后续可以连接但等待较久

第一份报告来自 2026-09-17，未包含版本号或完整启动时间。报告中先出现 Wintun
创建/打开网卡重试；12:02:30 网卡开始监听、多个规则源开始初始化，同一秒客户端
报告“分流规则尚未就绪”，稍后还有正常分流记录。证据支持当时存在启动时序问题，
不支持认定规则文件损坏，也不能据此计算整次启动耗时。

第二份报告为 Windows 5.0.11，核心、TUN 和数据通道均正常；近期连接流量覆盖了
启动日志，无法从附件还原耗时分布。当前代码已采用 45 秒 TUN 有界轮询，规则健康检查
通过即可继续，没有固定等待 45 秒。

本轮另外发现每轮轮询之前均调用 PowerShell 网卡身份查询，单次最多 6 秒；未取得
身份时会反复执行。它会阻塞本地 API/规则就绪观察，却不是判断规则是否就绪的必要条件。

调整为先轮询核心 API、规则及运行配置，再保存一次网卡身份，并在最终健康检查后提交
连接状态。启动前的持久化基线保护、失败清理、取消和最终进程身份检查均保留。
新增独立阶段耗时及“正在保存网络恢复信息”提示，用于下次实测区分驱动启动与身份记录耗时。
这减少了重复查询，不承诺具体提速秒数；驱动初始化和一次身份保存仍需要时间。

## 用户 B：抖音桌面版无网络，网页版正常

报告为 Windows 5.0.11。核心和 TUN 正常；失败日志明确为 `dial DIRECT`，命中国内规则，
随后发生 `bind6: An invalid argument was supplied`。维护者随后确认该电脑没有 IPv6 网络。
这是本机 IPv6 出口绑定失败的证据，不能归因为代理节点故障。脱敏报告没有进程名和完整目标，
不能证明所有这些请求均来自抖音；网页版可能自行使用 IPv4/回退，尚无浏览器抓包证据。

Windows 锁定 Mihomo 源码在 `component/dialer/bind_windows.go` 通过 `IPV6_UNICAST_IF`
绑定出口。该选项的接口语义见 [Microsoft 文档](https://learn.microsoft.com/en-us/windows/win32/winsock/ipproto-ipv6-socket-options)。
日志不能进一步区分物理网卡禁用 IPv6、接口不可用或索引状态异常。

TLS 嗅探默认不覆盖目标地址，因而可能保留原 IPv6 字面目标和已识别域名。原 DIRECT
拨号对这种请求不会根据嗅探域名尝试 IPv4；浏览器已经回退不代表其他应用也会回退。

Windows 核心补丁现在仅在 DIRECT TCP 拨号返回 `bind6` 错误、原目标为 IPv6、域名已知时，
用既有直连解析器查询 A 记录并补试一个真实 IPv4 地址。原 IPv6 成功时不增加解析或改变路径；
显式 hosts、内部 DNS 拨号、纯 IPv6 字面目标、未知域名和已取消请求保持原行为。
回退仍使用 DIRECT 的接口绑定和回环检查，共享原连接总超时，解析最多 2 秒。
不重放已发送的应用数据，不修改 TLS/SNI/Host，不改系统 IPv6 开关，不将代理失败改为直连。
没有 A 记录或备用解析失败时保留原失败，不能为 IPv6-only 目标创造 IPv4 地址。
本次只覆盖报告中的 TCP 绑定错误，不声称解决所有 UDP/QUIC 或抖音应用问题。

诊断增加本机 IPv6 出口的中文说明；一般 IPv6 提醒区分直连网络检查与代理节点检查，
避免让直连用户无效换节点。
