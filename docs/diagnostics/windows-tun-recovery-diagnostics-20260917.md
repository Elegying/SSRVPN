# Windows 5.0.7 网络恢复拦截排查

## 用户证据

截图显示 Windows SSRVPN 5.0.7，状态为“连接异常”，提示“上次连接的网络设置尚未恢复，请保持断开并再次尝试连接”。仅凭截图不能区分实际残留、检查失败和历史恢复记录不完整；也不能把当前节点名称当成节点故障的证据。

SS 节点问题按用户要求暂停，本次没有继续测试该节点。

## 已确认的代码问题及修正

1. 恢复检查超时后，底层异步查询仍可能完成。原服务在查询回调中直接更新恢复检查状态，过期结果可能重新标记待恢复。现在由等待器在超时边界内发布检查结果，超时只发布“检查失败”，底层查询的迟到结果不再更新恢复状态。
2. 原提示把“未能确认已恢复”写成了“尚未恢复”，且 Windows 诊断只列系统代理恢复，遗漏独立 TUN 恢复记录。新增“TUN 网络恢复”诊断项，分别说明存在网络地址/路由、无法读取系统网络状态、记录不完整、尚需连续确认。
3. 检查未完成时不再宣称 Windows 网卡未移除。诊断展示的是最近一次恢复检查的观察，不会为了生成报告自动清理网络或建立 VPN。

保留两次连续无残留确认、网卡身份检查以及启动前拦截。未自动删除网卡、路由或恢复记录。

## 证据边界

回归测试可重现并阻止迟到的检查结果重新改变已恢复状态。此问题是否正是截图用户的原因，仍需其脱敏诊断日志确认。尚未在该 Windows 设备上复现，未构建、安装或发布本次修正版本。

## 后续日志：同一电脑的两个阶段

用户随后确认两份报告来自同一个用户、同一台电脑：

- 第一份报告生成于 13:53，但最后连接尝试实际发生在 12:06:00–12:06:30。30 秒后在启动核心前因未能确认旧 TUN 已清理而中止；端口分配正常。现有 5.0.7 报告没有记录各次残留检查的分类，因此不能据此判定真实残留或查询失败。
- 第二份报告于 14:00 生成，核心 PID、控制 API 和 TUN 均在运行，说明该次启动已通过恢复检查。日志明确记录连接节点服务器端口的 TCP 超时。它不是仅有外部验证站点观察失败，也不是密码错误或 SS 加密失败的证据，因为这些尝试尚未完成 TCP 建连。
- 此报告使用 Fast-B1-1，与最初独立测试的 Fast-B1-4 不同，不能混用两条入口的测试结果。
- IPv6 REJECT 是另外的目标流量观察，不能仅凭它解释节点服务器连接超时。
- 用户反馈 Karing、FlClash、v2rayN 可用；尚未确认成功时的具体模式、DNS 配置与节点入口。

对照 FlClash 公开主分支 `lib/models/clash_config.dart` 的 DNS 模型：其节点域名解析默认只有腾讯 DoH，SSRVPN 配置生成器则同时写入国内 DoH 与普通 DNS。此项只建立可核查的配置差异，不能证明该用户实际配置或 DNS 故障，本轮未盲目更改 DNS/出站网卡策略。

新增诊断改进：对明确的 Mihomo 代理服务器 `connect error: dial tcp ... i/o timeout`，日志显示“这次未能连上节点服务器，请稍后重试或换个节点。”同时保留脱敏技术详情；核心 warning 不再因外层 INFO 包装而显示为普通信息。普通目标超时与 DIRECT 连接错误不会归为节点服务器故障。
