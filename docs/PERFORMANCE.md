# 性能基线

性能门禁关注“关键路径仍然能在有界输入上稳定执行”，不把某台机器的微秒数当作跨平台硬阈值。当前覆盖三条不依赖公网的共享路径：

- 解析单一 YAML 订阅；
- 合并多个订阅并处理名称和来源；
- 从合并结果生成 Mihomo 配置。

## 运行方式

快速结构校验已纳入 `make verify`：

```bash
make performance
```

采集可比较的本机基线：

```bash
cd packages/ssrvpn_shared
dart run tool/benchmark_critical_paths.dart
```

发布检查中的 `scripts/performance-baseline.sh` 继承调用者的 `PATH`，应先选择项目固定的
Flutter 3.44.1。子命令不再启动登录 shell，避免被系统的另一份 Dart 覆盖并改写依赖锁文件。

工具输出 JSON，包含输入节点数、来源数、输入/输出体积和各路径的最小、中位、最大耗时。`--smoke --verify` 使用较小样本并校验节点数和配置结构；任何无效结果都会以非零状态退出。

2026-07-14 的首个参考样本来自 Apple M1、macOS 26.5.2、Flutter 3.44.1：每来源 1200 个节点、4 个来源、7 次测量时，中位数分别为解析 17,358 μs、合并 92,825 μs、配置生成 174,603 μs。它只用于同环境后续比较，不是其他机器的通过阈值。

## 比较规则

只有以下条件同时接近时才比较耗时：

1. 同一操作系统、CPU 架构和电源模式；
2. 同一 Flutter/Dart 主版本；
3. 没有同时运行重负载任务；
4. 使用相同工具模式和 fixture 规模。

单次结果只用于定位，不用于宣称性能提升。连续三次基线的中位数都比同环境历史值高 25% 以上时，才视为需要调查的退化信号；先使用 profiler 找原因，再决定优化或记录合理变化。不得为了通过门禁降低输入规模、跳过输出校验或加入机器相关的宽松超时。

## 解释边界

该工具测量纯 Dart 共享逻辑，不代表真实订阅下载、磁盘、Mihomo 启动、VPN 建链或 UI 帧性能。上述路径应分别使用目标平台 profile 构建、系统性能工具和真机网络场景验证。Windows 11 真机矩阵仍按项目健康文档单独执行，不由本基线替代。

大订阅的网络响应格式识别与后续合并均复用可取消的后台处理组件；达到 256 KiB 的输入
在 worker 中识别 YAML/Base64/节点列表，兼容身份协商复用本次识别结果，避免返回时再次
解析。小输入继续使用原同步路径。回归测试验证界面事件队列有机会运行，以及取消后
不继续请求下一兼容身份、后台处理能够结束；这不等同于低配设备帧率或耗电实测。

启动、连接、断开、内存稳定性和空闲电量采用
[真机验收矩阵](UAT_MATRIX.md) 的统一采样与证据格式。尚未执行的设备项保持“未执行”，
不得用本页的纯 Dart 冒烟结果代替。


## 2026-09-13 UI 工作区优化

订阅列表使用惰性 SliverList；10、100、1000 条订阅的测试视口首次均挂载 4 张卡片。
节点按延迟排序在每次排序前读取一次快照，1000 节点用例包含可见行渲染共读取 1009 次。
这些数字是结构性成本证据，不是实际设备 FPS 或内存降幅。

玻璃使用稳定设备档位：普通设备 premium，保守识别的低性能设备 minimal + 60 帧。兼容着色器和高对比度路径仍保留，普通档背景采样分辨率未降低。
真实设备应使用 profile 构建和 `SSRVPN_FRAME_DIAGNOSTICS=true` 采集 build/raster P95、
超预算帧及实际产出帧率，分别覆盖 60/90/120 Hz、滚动、切页、弹窗、窗口缩放和前后台。
固定材质消除了自动换档造成的视觉变化，不保证低端 GPU 不掉帧；强动态背景的功耗也需真机记录。

节点页进入/退出期间暂停壁纸漂移，复用原纹理并更新采样原点，转场完成后恢复。
低档基于原生 vsync 时间戳统一限制绘制，保持真实动画时长；普通档不限制系统高刷新率。
Android 固定刷新率跟随系统设置，自动选择当前分辨率最高支持模式；省电/低性能请求 60Hz。
桌面使用当前窗口所在屏幕的原生合成时钟，不修改系统全局模式；DRR/ProMotion 的最高实际输出仍须实机验证。
低档识别阈值与未覆盖硬件类型详见本轮综合审查报告，不能视为 GPU 性能测试。
诊断区分 displayHz、targetFps、producedFps；刷新率变化会重开采样窗口。

2026-09-13 第二轮修订：玻璃几何只在真实布局/局部形状变化时重建，普通列表平移复用 SDF。
捕获背景且无内部玻璃内容的卡片跳过重复实时背景模糊。
物理测速共享 8 个在途请求及 64 个等待位置，客户端繁忙与远端失败分开显示和排序。
Android 除窗口偏好外也向 Flutter Surface 提交刷新率请求，后台释放请求。

## 2026-09-21 玻璃背景捕获节流

漂移壁纸此前每次重绘都会触发一次全屏离屏光栅化并新建一张全屏纹理。现在捕获按
`SchedulerBinding.currentFrameTimeStamp` 节流到 100 毫秒窗口：窗口内的重绘只复用
上一张纹理并更新取样原点，窗口外或离散事件（首个捕获、devicePixelRatio 变化、
重新启用、从后台恢复）仍立即重新光栅化，静止或暂停的壁纸依旧完全不捕获。

`glass_capture_scheduling_test.dart` 新增回归：同一个 480 毫秒窗口内，漂移壁纸的
重绘次数不变，捕获次数由每帧一次（30 次）降为 5 次。这是结构性成本证据，不是真机
功耗或帧率实测。高档玻璃内背景的刷新率上限由此受 10 Hz 约束，需按上文方式在真实
设备确认漂移在被模糊的背景中无可感知跳步；低档、高对比度、自定义与纯色背景路径
不经过该捕获，逻辑不变。

真机量级（Apple M1 / 8 GiB，同机同订阅，高档玻璃 + 漂移壁纸，窗口 380×793 且保持
前台、未连接）显示该节流的净效果约为 2 个百分点（单核），见下节。漂移壁纸本身的
逐帧渲染才是空闲功耗的主体，节流只削减其中的捕获部分。

## 2026-09-21 静止壁纸默认（真机 CPU 实测）

把三端默认外观从流动壁纸改为静止壁纸后的资源对比。测量条件：Apple M1 / 8 GiB、
同一订阅、380×793 窗口保持前台且未连接、高档玻璃，采样口径与
`docs/uat/SSRVPN_实机资源测试_20260914.md` 一致（预热 20 秒，随后 30 秒 `top`
每秒采样、再 30 秒 `ps` 累计 CPU 时间差）。每个样本同时用两种方法取值，两者相差
均在 1 个百分点内。

| 外观 | 单核 CPU 占比 | 样本数 |
| --- | ---: | ---: |
| 官方 5.0.13 默认（流动壁纸） | 35.25%（34.63 / 35.87） | 2 |
| 静止壁纸（新的默认值） | **0.32%**（0.333 / 0.300） | 2 |
| 壁纸 + 「动态背景」开启 | 33.36%（33.00 / 33.13 / 33.07 / 33.67 / 33.93） | 5 |

静止壁纸的空闲 CPU 落到噪声量级，且该状态下不再产生任何帧诊断输出（无帧产生）。
窗口被遮挡时旧默认也会回落到同一量级，说明持续渲染只在窗口可见时才会付费。

同一会话内的配对测量用于隔离两项改动：以同一份源码只翻转节流常量（100 毫秒对
零）得到 34.92% 与 33.13%，即捕获节流自身约 2 个百分点；节流关闭版与未修复的官方
构建读数一致，说明该变体忠实复现了修复前行为。

这些数字不能与 2026-09-14 基线（界面版本 5.0.1、482×795 窗口、16.7%）直接比较：
版本与窗口尺寸都不同，且未做同条件对照，因此不声称回归或提升百分比。测量期间发现
一个会污染样本的因素：被测量的窗口一旦失去前台地位，漂移会自动暂停，读数会显著
偏低；采样脚本已通过前后两次前台核对识别并剔除这类样本。
