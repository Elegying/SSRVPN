# SSRVPN 项目硬性规则

本清单是当前开发、审查、测试和发布的强制约束。规则来自已接受的 ADR、用户明确决策、
安全策略和现有回归门禁，不是建议项。任何改动若需要突破本清单，必须先取得维护者明确确认，
更新对应 ADR、测试、用户文档和回滚方案后才能实施。

## 1. 产品范围与平台

1. Android、macOS 和 Windows 的主导航只保留“首页/主页”和“订阅”两项；不得恢复隐藏的解锁测试、后台检测服务或替代性实验入口。
2. 三端保持同一核心流程：导入订阅或节点、选择节点、建立连接、查看状态、断开连接；平台差异只用于操作系统集成。
3. Android 正式包最低支持 Android 7.0，仅发布 `arm64-v8a` APK，并必须保持同一正式自签名证书谱系。
4. macOS 正式包最低支持 macOS 11，仅支持 Apple M 系列 `arm64`；不得宣称支持 Intel 或 `x86_64`。
5. Windows 最低支持 Windows 10 1507（build 10240）x64，只发布每用户安装器 `SSRVPN_Setup.exe`，不得恢复便携 ZIP 发布链。
6. macOS 固定采用 ad-hoc、未公证免费分发；Windows 固定采用未签名安装器。除非维护者明确取代该决策，不引入 Apple Developer ID、公证、Authenticode、付费证书 secret 或对应自动化。

## 2. 安装、升级与用户数据

7. macOS DMG 根目录必须包含 `SSRVPN.app` 和指向 `/Applications` 的快捷方式，支持拖拽安装。
8. Windows 固定安装到 `%LOCALAPPDATA%\Programs\SSRVPN`，不提供安装目录选择；安装阶段可以请求管理员权限，但不得因此改装到 Program Files。
9. Windows 覆盖升级、卸载和保留数据后的重装必须保留安装版订阅、设置、DPAPI 密钥、LocalAppData 回退数据和窗口状态，只替换已知程序文件。
10. Windows 安装器不得搜索、迁移、合并、修改或删除桌面、下载目录及其他位置的旧独立副本；存在其他运行中副本时，应在改动系统代理前停止安装并提示用户自行退出。
11. 安装、卸载、退出和异常恢复只可结束路径、PID、会话、创建时间和所有权能够证明属于当前 SSRVPN 安装的进程；不得按 Clash、OpenVPN、WireGuard、Tailscale、ZeroTier 等通用名称结束第三方软件。
12. 安装或升级事务不明确时必须失败关闭并保留用户数据、安装包和恢复证据，不得用猜测性清理换取继续安装。

## 3. 订阅与节点数据

13. 首次打开或没有节点时，应用必须引导用户导入订阅链接或节点链接；成功导入后自动刷新、加载节点并开始测速。
14. 订阅输入、重定向、DNS 解析、响应头、响应体、编码、节点数量和解析深度必须有界；HTTPS 重定向不得降级到 HTTP，证书校验不得被生产代码绕过。
15. 为兼容现有服务，订阅入口继续接受合法 HTTP 与 HTTPS 地址；界面和用户指南必须推荐 HTTPS，不得把 HTTP 描述为具有传输保密性。
16. 刷新或导入失败不得破坏最后一份可用订阅。多订阅刷新部分失败时必须区分成功和失败来源，不得把部分成功误报为全部成功。
17. 订阅名称或链接编辑成功后刷新对应节点，并保留订阅启用与自动更新设置；链接变化时不得沿用不再可信的旧更新时间。
18. 订阅、节点、设置和 secret 的写入必须采用平台已有的串行化、原子替换和失败保留边界，不得先删除唯一可用旧数据再尝试写入新数据。

## 4. 节点选择与延迟

19. 节点延迟统一只测 `TCP Socket.connect(节点服务器, 节点端口)`；不得改为经 Mihomo、代理 HTTP、目标网站状态码或完整协议握手测速。
20. 测速必须有超时、取消、并发上限和结果代际；旧测速结果不得覆盖刷新、删除或重新导入后的新节点状态。
21. 测速超时节点必须置底、变灰并保留检查或编辑入口；未连接时仍允许预选可运行节点，已连接后的实时切换只允许当前未超时节点。
22. 节点默认保持订阅原始顺序；只有用户主动点击排序按钮时，当前页面才按延迟升序显示，再次点击恢复默认顺序。排序不得写回订阅、节点配置或记忆节点。
23. 应用必须记忆最近一次选择的节点；Android 快捷磁贴连接沿用该节点，不得因为尚未测速或一次测速超时静默改选其他节点。

## 5. 建连、健康与恢复

24. 只有核心进程、受认证本地 API 和目标平台的 VPN、系统代理或 TUN 均确认就绪后，界面才可显示“已连接”；端口开放或启动命令返回不能单独作为成功依据。
25. 建链必需条件、本地核心存活和连接后的外部可达性必须分层。外部站点暂时不可达只能产生建议性提示，不得据此自动断开、重启核心或切换节点。macOS TUN 授权取消或超时必须返回可重试状态，不得自动降级到用户未选择的模式。
26. “连接中”必须允许取消。取消、重复点击、旧代际回调、迟到权限结果或旧健康探针不得覆盖更新一代连接状态。
27. Android 核心意外退出最多执行一次受控恢复；恢复中和最终失败必须明确通知，用户主动断开不得触发自动重连。
28. macOS 和 Windows 的系统代理只在仍由 SSRVPN 持有相同端点时恢复；用户或其他软件后续修改的代理设置不得被覆盖。
29. 端口冲突自动改用临时 mixed、SOCKS 或 API 端口时必须向用户列出实际变化；下一次未调整时不得继续显示旧提示。
30. 三端对未配置、连接中、已连接、断开中和失败的语义必须一致；错误提示应使用稳定分类和可执行建议，不直接显示原始异常或敏感值。

## 6. 路由与网络

31. 三端只提供全局模式和规则模式。规则模式固定遵循“用户强制代理优先、国内直连、国外及未知流量兜底代理”的顺序。
32. 强制代理域名必须同时使用代理 DNS，并排在国内域名、`.cn` 和 GeoIP 直连规则之前；强制代理 IP 只生成 IP 路由规则。
33. 三端运行配置永久保持 IPv4-only：关闭 Mihomo 和 DNS IPv6，不生成 IPv6 Fake-IP；首页公网 IP 只展示 IPv4。
34. Android 与 Windows TUN 必须捕获并拒绝 IPv6，防止绕过；macOS 只关闭 Mihomo 内部 IPv6，不修改操作系统全局 IPv6 开关。
35. 国内域名集和 `geoip.metadb` 必须固定来源、校验摘要并由三端使用同一份发布资产；HTTP、TLS、QUIC 域名嗅探必须有界且不得全局改写目标地址。规则或数据库不可用时不得静默改变既定路由优先级。

## 7. 更新与发布来源

36. 三端只有在节点连接成功或恢复连接态得到确认后才能检查更新；未连接启动、首页初始化或未知恢复状态不得发起更新请求。
37. 应用内更新只接受 `Elegying/SSRVPN` 正式 GitHub Release 的规范平台资产及同名 SHA-256；元数据、资产名、tag、下载 URL 或摘要不匹配时失败关闭，不得回退 OSS。
38. 发现新版时只在底部版本号旁持续显示“发现新版本 立即更新”；未经用户点击不得自动打开更新页、自动安装或强制退出。
39. 下载必须显示进度并允许取消；只有完成 SHA-256 校验的文件才可发布到目标位置或交给系统安装，失败和取消不得损坏已有目标。
40. Windows 只可清理由 v4.0.15 或更高客户端内置更新器下载、校验、写入专属标记且安装事务成功的版本化安装包。旧客户端、手动下载、取消、失败、身份不匹配、非普通文件和同目录其他文件必须保留。标记遗留后的同版本重下必须使用由规范文件名和可信 SHA-256 派生的独立备用名，不得认领或覆盖旧标记；中断恢复候选只读且必须保留原文件。
41. OSS 只作为网站、人工分发、不可变归档和发布事务镜像；不得重新成为客户端更新权威或静默备用源。

## 8. 安全、隐私与诊断

42. `apiSecret` 不得写回普通设置 JSON。Android 使用安全存储，Windows 使用当前用户 DPAPI，macOS 使用权限为 `0600` 的独立文件，并按各平台既有迁移和失败回滚边界处理。
43. 日志、错误、剪贴板诊断和崩溃报告必须限长并经过共享脱敏；订阅 URL、Token、密码、Authorization、用户目录和公网地址不得原样进入可分享内容。
44. SSRVPN 不内置遥测，不自动上传日志、崩溃报告、订阅或节点数据；诊断由用户主动查看、复制并在分享前复核。
45. macOS TUN 管理员授权按次生效，SSRVPN 不读取或保存系统密码；临时 root runner 必须绑定当前应用会话并在断开、退出或失败时清理。
46. 动态状态不得只靠颜色表达；关键按钮、错误、进度和对话框必须具备可读语义、合理焦点顺序，并支持窄窗和大字号滚动关闭。节点页订阅筛选和延迟排序必须保持为两个独立点击区域；订阅选择、“关于”和“使用教程”继续使用统一透明毛玻璃表面。

## 9. 工程、测试与发版

47. `main` 必须保持严格分支保护、线性历史、禁止管理员绕过、禁止 force-push/删除，并维持版本化策略规定的九项必需检查。
48. 正式发版必须绑定精确 `main` 提交、版本号和 CHANGELOG；只有完整门禁通过后才能创建不可变 annotated tag，已推送 tag 不得删除、移动或复用为另一提交。
49. 正式 Release 必须包含 APK、DMG、Windows 安装器、三个 SHA-256 和 provenance；GitHub Release、OSS 不可变目录、固定下载地址和 `latest.json` 必须属于同一事务并可回滚。GeoIP 只在正式发版准备阶段刷新并写入可复现来源记录，不恢复每日自动更新或在 tag 构建中动态追随 `latest`。
50. 自动化测试、平台构建 smoke、人工实机 UAT 和线上公开资产必须分别记录；任何一类证据不得冒充另一类已经执行。
51. 新增或修改用户行为必须增加最小行为回归，并断言用户最终状态、数据保留和系统网络设置；只验证函数返回或进程启动不算验收。
52. 高风险生命周期、安装、代理恢复和 VPN 事务只按有行为证据的职责渐进拆分；不得仅为减少行数改变执行顺序、所有权、回滚或失败关闭边界。

## 规则变更流程

1. 明确记录要改变的规则、用户价值、兼容影响和安全风险。
2. 取得维护者明确确认；重大或昂贵可逆性低的变化新增 ADR，旧 ADR 保留并标记被取代。
3. 先补行为测试和回滚路径，再修改共享实现与平台实现。
4. 同步本清单、[功能列表](FEATURES.zh-CN.md)、用户指南、CHANGELOG、UAT 和发布门禁。
5. 在受影响目标平台完成自动化、构建和必要实机验证后，才可进入正式发布。
