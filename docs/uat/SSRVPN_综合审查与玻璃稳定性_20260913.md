## 玻璃为什么看起来不稳定

### 1. 已确认：性能自适应会更换材质路径

共享入口此前默认启用自适应质量。运行时连续超预算窗口会降档，恢复后又可升档。premium、standard、minimal 不只是计算精度不同，分别可能使用完整折射、轻量着色器、磨砂回退。共享玻璃卡片也会随质量改变是否使用背景捕获层。因此相同控件的折射、模糊与色调可能在使用过程中变化。

根据后续验收反馈，改为启动时确定稳定设备档位：普通设备固定 premium，低性能设备固定 minimal 并使用共享 60 帧节奏控制。普通档原有完整折射参数、设备像素比和采样分辨率不降低。`SSRVPN_GLASS_ADAPTIVE=true` 可显式恢复诊断用自适应，`SSRVPN_GLASS_FIXED_PREMIUM=true` 优先关闭适配。高对比度与设备不支持完整着色器的兼容处理仍保留。

固定材质解决换档引起的外观变化，不自动解决 GPU 过载。低端或温控设备可能仍掉帧；必须靠减少工作量与实机 profiling 继续优化。

### 2. 已确认：Android 切页期间改变了页面高度

Android 使用 PageView，桌面使用保留页面的堆栈。此前 Android 根据当前页索引切换 `extendBody`，滑动越过中点或点击导航时可能重新分配整个 PageView 高度，导致控件布局和采样边缘跳动。

本轮固定 Android 滑动区域高度；主页局部预留导航栏空间并恢复原始系统 inset，订阅页允许滚动到导航后方，同时在列表尾部保留避让空间。没有移除滑动操作。

### 3. 已确认：共享组件不等于完全相同的底层绘制

Android manifest 启用了 Impeller；实际渲染器仍按能力检测决定是否使用 shader filter。共享库在不支持完整路径时使用轻量着色器，并对光学参数做兼容映射。Windows、macOS、Android 的字体栈、设备像素比、刷新率和 GPU 后端也不同。

目标应是稳定的层次、可读性、交互和近似光学表现。当前证据不能保证所有后端逐像素一致，也不能把未知的黑块/闪烁全部归因于质量切换。

截图复核时，首次 macOS 主题的离屏主页图曾出现部分前景缺失；同一脚本原样重跑后恢复完整，未稳定复现。尚不能确定是测试捕获/异步绘制时序还是实际产品渲染问题，列入原生首帧验收重点，不能凭后一次完整截图关闭该观察项。

### 4. 仍需实机判断：移动背景、纹理与帧耗时

背景先绘制，再通知采样层使用新纹理；这一同步链受真实合成与 GPU 调度影响。当前实现复用静止纹理、只更新平移原点，绘制完成后才捕获，并延后释放旧纹理。相关生命周期和 shader 边界测试会继续覆盖。代码检查尚不能证明本轮每台设备都没有快滚黑块或一帧采样滞后。

## 后续验收反馈与修订

### 账户信息与连接光晕

首次手动验收打包漏传 `config/ssrvpn-usage-defines.json`，导致私家车账户 provider 为空、两张统计卡片不可见。正式 CI 已有该配置；本地三端构建说明现已补齐参数。第二份 Android 和 macOS 验收包检查了 AOT 中的配置存在性，未输出配置内容。macOS 实际连接和 Android 只读界面检查均确认“已用流量”“已连接设备”恢复。

连接开关新增 2.6 秒局部扩散光晕，外层画布限定为按钮的 1.26 倍；只有正常已连接时运行，断开、错误、后台、被覆盖及减少动态效果时暂停或隐藏。绘制独立于按钮构建，无全屏滤镜。

本机 macOS 已检查连接/断开、主页/订阅返回、关于弹窗、快速滚动和窗口放大恢复。未观察到之前离屏截图的前景缺失；这不能证明所有设备都不存在同类问题。

### 节点页转场与刷新率（本轮新增）

Android 实机旧验收包的静止 60Hz 批次约 60 FPS，raster P95 约 3ms；操作期间高刷新批次出现 raster P95 约 16–35ms、产出约 74–97 FPS。批次没有隔离动作，不能当作节点转场的精确基线，也不能声称新版本已稳定 120 FPS。

节点页转场期间暂停壁纸漂移，页面玻璃沿用原清晰度纹理，只更新采样原点；转场完成后恢复背景。未引入整页透明度层或降低普通档玻璃质量。

Android 原生窗口请求遵循固定刷新率设置；已识别的自动模式或无有效固定值时选择当前分辨率最高支持模式，取消写死的 120Hz 上限。系统设置监听覆盖通用 peak/min 以及当前设备使用的 MIUI 设置。省电或低性能时请求 60Hz；硬件不支持 60Hz 时使用最低可用模式，再由共享节奏控制限制绘制。其他厂商未公开的自动模式字段仍需实机验证。

三端低档检测采用保守硬件启发式：Android 系统 low-RAM 标记、总内存不超过 3GiB，或小堆（不超过 128MiB）且 CPU 最高频率不超过 2.1GHz；CPU 信息不可读时小堆作为保守回退；桌面总内存不超过 4GiB 或逻辑处理器不超过 2。未知硬件保持普通档。这不是 GPU 跑分，不能识别所有“内存大但 GPU 弱”的设备，后续需真实低端设备校准。

三端低档共用基于原生 vsync 时间戳的 60 帧调度，不改变动画时长，也不更改系统全局显示设置。普通桌面继续由 Flutter 原生合成时钟驱动；读取当前窗口所在屏幕的频率用于诊断。系统自动模式下的最高实际输出仍受引擎、系统合成器、驱动、省电与温控约束，Windows DRR/macOS ProMotion 未完成本轮高刷新真机验收。

刷新率切换时清空混合统计窗口，诊断分别记录显示 Hz、目标 FPS 与实际产出 FPS。新增共享专项 17 项及 Android 刷新率原生规则测试通过。后续安装、实机结果单独记录；正式发布仍暂停。

### 第二轮反馈：仍有卡顿、底部“测速繁忙”

刷新率修订验收版已安装无线 Android 和本机 macOS。无线窗口确认请求约 120Hz，稳定批次实际约 120.45 FPS、raster P95 3.50ms、零超预算帧；操作批次仍出现约 22–28ms raster P95，用户确认“有改善，但仍有卡顿”。本轮不能据此关闭掉帧问题。

继续检查并修复两项玻璃重复工作：`layout()` 被重复调用但尺寸未变时，不再强制重新生成形状纹理；图层整体平移时比较局部形状和变换，复用相同几何纹理。捕获背景且内容在玻璃上方的卡片省去被捕获着色器覆盖的实时模糊读取；有内部玻璃内容或无捕获的路径保留原处理。

“测速繁忙”来自原生并发上限，并非远端节点故障。取消一轮 UI 测速不会立即终止已有原生 DNS/socket 工作，新轮叠加可能撞上 16 个线程上限。共享物理测速入口现在跨实例限制为 8 个在途任务，其余进入最多 64 个的有界队列，等待超时仍明确返回客户端繁忙。忙碌状态使用中性色，不再按节点故障排序或禁止选择。30 个重叠请求的回归测试确认原生并发峰值为 8；等待超时释放队列位置。

新增 USB 设备为 Redmi Note 8（Android 11，arm64），总内存约 5.5GiB、CPU 最高 2.016GHz、应用堆配置 128MiB。它用于校准低档检测，避免仅看总内存将旧 GPU 手机误判为高性能。安装与实际帧率以随后设备记录为准。

### 低性能真机追加验收

两台 Android 已安装同一份带几何缓存/测速排队的预览 APK。Redmi Note 8 日志确认 `lowPerformance=true frameCap=60`，无线高性能机为 `lowPerformance=false frameCap=system`。低性能机初版持续画面仍只有约 12.6 FPS、raster P95 约 82–84ms，说明库的 minimal 回退仍包含实时模糊，不能把“识别为低档”当作达到 60 FPS。

据此继续精简低档路径：卡片使用半透明颜色与边框，底栏使用简单导航，移除实时模糊、玻璃自定义着色器及模糊阴影；局部径向光晕保留。普通设备仍使用原玻璃效果。相关 60 项回归通过；后续实际帧率另记。

无线机合成器已观察到约 120Hz 的应用请求，但系统仍会给出 60Hz 的运行阶段。应用请求与系统最终调度分开记录，不更改用户全局设置，也不宣称能够绕过 OEM、省电或温控限制。
