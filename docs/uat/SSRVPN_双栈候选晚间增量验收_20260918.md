# 双栈候选晚间增量验收（2026-09-18）

本轮目标：macOS / USB Android 安装验收，并同步源码供维护者在 Windows 构建验证。
不是正式发布验收，不创建标签或发布安装包。保留所有既有工作及正式版用户数据。

## 候选范围

源码基线 `b801970466673a6c034fab37e571b80159e5bd39`，分支
`codex/dual-stack-startup-reliability`，PR #254。本报告随候选提交保存。

- DIRECT 的 DNSMapping AAAA 恢复域名；TCP / UDP 复用核心原生解析和地址族选择。
- 物理接口明确只有 IPv4 时，DIRECT 域名优先有效 A；不影响代理出口 IPv6，不增加外部阻塞探测。
- 桌面连接成功后等待 5 秒，三个独立端点最多两轮，全部失败才提示；失败不停止核心或改为直连。
- 验收中新发现的启动调度问题：确认节点导致 route epoch 改变，绕过原先 5 秒延时；现保留同会话启动截止时间。
- 验收中新发现的重复选中问题：目标节点已生效仍 PUT 并 DELETE 全部连接；现先核对 PROXY 与有效出口，同节点确认保留现有请求，实际换节点仍清理。
- 桌面公网 IP 查询立即发起；短暂失败仅自动重试一次，断开/新会话取消旧结果；最终失败明确提示 IP 查询未完成，不宣称节点失效。
- 公网 IP 运行记录只记结果类别和耗时，不记录 IP、订阅、密码或原始异常。

- 未做 Mac 断网验收；未断开物理 Wi-Fi、重置网络或修改路由器。

## 桌面首次请求失败追查（追加，尚待新核心实机确认）

Mac 旧候选在核心就绪后，首次公网 IP 查询 16 秒失败，有限重试仍失败；
约两分钟后的手动查询耗时 1.13 秒成功。当前同一连接上，显式混合代理和
TUN 默认路径访问同一 IP 查询端点均 HTTP 200（约 0.55 / 0.61 秒）。
这是启动期问题线索，不是节点永久不可用的证明。

源码确认 Mac / Windows 的延后 TUN 提交实现中，`loadProvider` 会先启动
内置节点健康检查。`CompatibleProvider.Initial` 立即启动健康检查，可能创建
可复用的节点传输；此时 TUN 构造尚未安装自动物理出口选择器。Android 使用
系统 socket 保护，不能用其正常结果推断桌面正常。

本次最小修正仅延后桌面内置节点提供器的健康检查，直到 TUN 提交且核心进入
运行状态。文件和 HTTP 提供器仍按原顺序准备，系统代理模式顺序不变；
不修改分流、不关闭 IPv6、不允许 PROXY 失败转 DIRECT、不关闭 TLS 校验。
新增 Go 回归覆盖内置检查延后、远程提供器准备保留、系统代理语义和仅初始化
一次，并通过脚本门禁检查两个桌面补丁的实际调用位置。

此处确认的是启动顺序缺陷与修正；它是否完全解释 Mac 当前反馈，需以重建
安装后的首次连接结果为准。Windows 没有本机实测，不宣称其症状已复现或已通过。
