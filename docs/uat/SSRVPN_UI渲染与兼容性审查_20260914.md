# UI 渲染与兼容性审查

日期：2026-09-14。用户反馈：5.0.1 在配置不高的 Android 9 手机和 Windows 10 电脑上所有界面卡顿，非网络或连接卡顿；具体设备型号未知。

## 定位与改动

对照本地 v5.0.1 标签，确认旧版 lightweight 玻璃渲染器每次绘制创建一个新的 BackdropFilterLayer。页面壁纸持续移动时，多张卡片会分别进行背景模糊。高分辨率和较弱 GPU 会放大这部分成本。这是代码中确认存在的重复工作，不能替代受影响设备的故障复现。

[Flutter 的渲染器说明](https://docs.flutter.dev/perf/impeller)说明 Android API 29 以下使用旧 OpenGL 渲染路径；本项目使用 Flutter 3.44.1。不要把较新 Flutter 文档中的桌面默认配置直接套用到当前工具链，也不应仅凭系统版本给设备降画质。

本轮改动：

- 重绘复用 BackdropFilterLayer；不再使用模糊或组件移除时释放引用，避免逐帧重新分配及旧图层滞留。
- 固定画质上下限时，不再启动自适应帧耗时收集；可动态调整画质的使用方式保持原行为。
- Android 和桌面端手动检查发现新版本后，沿用已有底部“发现新版本／立即更新”入口，移除重复浮条，并立即清除已有提示。旧提示不会继续盖住更新按钮。

没有降低模糊强度、透明度、分辨率、动画频率或高配设备画质，也没有改变原有设备分档。现有分档只用内存、CPU 等粗略信号，不能代表 GPU 的真实性能；本轮没有扩大低画质设备范围。

## 稳定性与兼容性验证

- 两张玻璃卡片在 30 次内容重绘中复用原模糊图层，恢复相同内容后实际渲染像素完全一致；组件移除无异常。
- 现有玻璃测试覆盖纹理复用、页面移动、大小变化、暂停恢复、资源释放、Shader 到达时表单状态保留及玻璃边缘采样。
- 共享全量测试覆盖小屏、大字体、非线性字体缩放、桌面窗口持续调整、横竖向布局、卡片尺寸稳定、60/90/120 Hz 帧节奏和无障碍布局。
- 10/100/1000 条订阅列表可见区域构建测试通过；1000 节点排序避免反复读取全表延迟。没有为了优化重新改写已经受测试保护的列表逻辑。
- 真实桌面关于页通过模拟 GitHub 更新响应验证手动检查，发现新版本后没有遮挡底部的 SnackBar。

本轮没有连接到 Android 实机，也没有 Windows 10 运行主机。因此不能据此声明两个反馈设备已经恢复流畅，也不能给出三端统一“全局帧率”。高低配设备的实际帧率、GPU 驱动差异、温度和耗电需要 Profile/Release 候选包实测。

## 测量方法

独立 macOS Profile 程序使用本仓库 lightweight 渲染器、7 张玻璃卡片及持续移动背景，按“未分组 → 分组 → 未分组”三个阶段测量。每段 12 秒，前 2 秒预热；记录 UI 构建与光栅化 P95。程序不加载正式客户端数据或启动 VPN。这是算法对照，不是完整 SSRVPN 页面帧率，更不是 Android 9 或 Windows 10 实测。

测试程序：`/tmp/ssrvpn-render-audit-20260914/lib/main.dart`；运行日志：`/tmp/ssrvpn-render-audit-runtime.log`。首次写入沙盒外路径失败的测量已作废，改用日志输出后重测。

实测结果：

| 阶段 | 帧数 | UI 构建 P95 | 光栅化 P95 | 光栅化超过 16 ms |
| --- | ---: | ---: | ---: | ---: |
| 未分组 | 602 | 0.573 ms | 3.430 ms | 0 |
| 分组 | 602 | 0.568 ms | 3.418 ms | 0 |
| 再次未分组 | 593 | 0.574 ms | 3.447 ms | 0 |

没有显著提速。进一步核实 [Flutter 3.44.1 Skia 实现](https://github.com/flutter/flutter/blob/3.44.1/engine/src/flutter/display_list/skia/dl_sk_canvas.cc)，SaveLayer 接收 backdrop_id 但未使用。因此撤销本轮试验性的 BackdropGroup 及三个列表/卡片调用点，仅保留图层复用和固定画质统计优化。这组数据用于否定无效方案，不是最终补丁相对 5.0.1 的性能提升证明。

低配设备全界面卡顿仍未完成复现与修复验收。动态壁纸下的逐卡片模糊是待实机量化的热点；不能只凭代码认定为用户卡顿的唯一原因，也不能宣称已彻底解决。后续应使用同一候选包测首页静置、节点滚动、页面切换和窗口缩放，分别记录 UI/raster P95、掉帧比例和内存。若模糊被确认占主导，再实施背景预模糊缓存，并验证滚动、遮挡、窗口缩放和视觉一致性。

## 第二轮：全局效率与兼容性复审

本轮重新追踪了共享背景捕获、背景动画、首页文字适配、流量采样、原生设备分档、Windows DPI 处理和帧节奏实现。

| 范围 | 当前结论 | 证据与限制 |
| --- | --- | --- |
| 首页 CPU 布局 | 已减少重复字号测量 | `SsrvpnHomeText` 原先每次重建进行 1–11 次 TextPainter 测量；现在每个挂载组件只缓存最近一组输入。固定参考文本、相同布局下更新数字可复用字号。仍需正常绘制新文字。 |
| 缓存有效性 | 尺寸、样式、缩放、方向、参考内容及系统字体更新均使缓存失效 | 不保留 TextPainter、图片或不断增长的历史结果；销毁时解除字体监听。 |
| 动态背景 | 已有前景隔离及生命周期暂停 | 背景只移动自身，页面遮挡、后台、减少动态效果时停止；不能据此断言所有 GPU 都能流畅运行。 |
| 玻璃采样 | 高分辨率成本仍是重点 | 支持共享 Shader 的路径在背景变化时按设备像素比捕获背景；静态背景和仅页面原点变化可复用纹理。动态背景仍需持续捕获。 |
| 旧渲染器 | 每卡模糊仍存在 | 上轮已证实当前 Skia 未实现背景分组合并，不再次接入无效分组。 |
| 流量显示 | 无并发轮询堆积 | 一次采样结束后再安排下一次；后台或页面不活跃时停止，旧轮次结果被丢弃。连接空闲时仍按秒采样，并非零开销。 |
| 全局帧节奏 | 调度策略测试通过 | 60/90/120/144/165/240 Hz 输入下的低配 60 帧调度、闲置后恢复和回调配对通过。这是调度测试，不是 GPU 实际帧率。 |
| Android 分档 | 只能粗略判断 | 低内存设备、约 3 GiB 总内存门槛及部分 CPU/内存组合；未直接测 GPU。既有低配模式使用 minimal，本轮未扩大分档或降低任何画质。 |
| Windows 分档与 DPI | 已有适配，仍需驱动环境验收 | 分档检查内存和逻辑 CPU；应用声明 PerMonitorV2，并处理 WM_DPICHANGED。跨显示器实际缩放与旧显卡驱动尚未验证。 |
| 尺寸和可读性 | 本轮自动化覆盖通过 | 小屏、横屏、大字体、长设备数字、不同宽度和持续窗口缩放；不能替代全部手机刘海、折叠屏和 OEM 字体实机验收。 |

### 新增修复验证

- `home_text_cache_test.dart` 将保留状态的缓存文本与每次重新创建的文本逐轮比较，覆盖 16 组内容、约束及字体变化，字号与布局尺寸一致。
- `/tmp/ssrvpn-ui-second-review.log`：213 项通过，包括上述测试及流量卡片、账号布局、背景动画、玻璃生命周期、导航布局、帧节奏测试。与前轮测试存在重叠，不累计为独立总数。
- 本轮没有获得新的 Android 9、Windows 10 实机 GPU 测量；不能给出实际全局 FPS、耗电改善百分比或大幅减负结论。

### 后续方案优先级

1. 优先测量原分辨率下的动态背景、玻璃和前景各自耗时，再决定是否实施共享预模糊背景。保持效果需要保留模糊边缘扩展、坐标映射、颜色和弹窗层级；直接把所有卡片换成一张模糊图会有采样差异，当前不采用。
2. 静态背景纹理及固定几何的复用有价值；现有捕获器已做部分复用，避免再叠加第二套缓存和逐帧复制。
3. 不将降分辨率、降低模糊强度、停止可见背景动画或扩大 minimal 设备范围作为“同效果优化”。
4. 发布验收应分别记录 UI 与 raster P95/P99、超过目标帧预算比例、持续滚动与缩放、前后台恢复、内存稳定性。60/90/120 Hz 的单帧预算约为 16.67/11.11/8.33 ms，不能统一套用 16 ms。
