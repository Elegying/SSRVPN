## 实际帧耗时

只选取完全落在采样时间范围内的诊断窗口，排除初始化等待和跨场景窗口。范围表示多个窗口各自 P95 的最小值至最大值，不是将其合并后的总体 P95。

| 场景 | 窗口帧率 | UI build P95 | raster P95 | 超帧预算比例 |
| --- | --- | --- | --- | --- |
| 首页 | 59.50–59.75 FPS | 3.13–3.63 ms | 12.30–16.41 ms | 34/1455，约 2.3% |
| 连续滚动 | 58.29–59.03 FPS | 2.42–3.08 ms | 18.24–19.38 ms | 182/1319，约 13.8% |

超帧预算指 build 或 raster 超过约 16.67 ms，不等同于屏幕实际丢帧数。接近 60 的平均帧率无法消除长帧造成的不均匀感。本机滚动时 raster 明显高于 build，说明渲染阶段是本次数据中更突出的压力来源；无法仅凭这些指标进一步断定某个具体 Shader 或 GPU 单元是唯一原因。

## GPU 指标限制

Android 11 的 dumpsys gpu 未提供上一台 Android 17 手机的应用 UID GPU 活跃时间和进程 GPU 内存表；kgsl gpubusy/gpuclk 读取返回 Permission denied。未获取 root 或修改系统权限，因此 **GPU 占用率、GPU 活跃时间比例及独立驱动显存未测得**，不能用 raster 时间替代。

内存诊断的 Graphics PSS：首页约 84.72 MiB，滚动约 84.80 MiB。这是图形内存统计类别，并非完整独立显存，也不能再与 TOTAL PSS 相加。

## 对照与结论

- 上一台 Android 17 高配手机：首页 CPU 56.4%、滚动 98.9%，默认画质不同，因此 Redmi CPU 数字较低不能说明其渲染能力更强。
- 上一台首页稳定窗口 raster P95 约 2 ms；Redmi 首页约 12–16 ms，滚动约 18–19 ms，即使已进入低配模式，渲染余量仍偏小。
- 本次确认了老设备存在渲染长帧压力，而后台停止高负载工作有效。不是 Android 9 设备，也不是此前原版 5.0.1 的同条件 A/B 测试，不据此声称该反馈已彻底修复。
- 本轮仅测试，未修改源码、提交、推送或发布。测试完成后关闭预览进程、HTTP 服务和 USB 转发；独立测试应用及虚构订阅保留，便于后续复测。
