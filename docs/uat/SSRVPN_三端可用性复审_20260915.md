# SSRVPN 三端可用性复审（2026-09-15）

## 范围与结论

以本地 5.0.4 源码（8c325ba）和既有未提交的规则回退补丁为基础，追踪共享连接协调、三端启动入口、健康监控、规则下载/下次连接应用、失败回退、端口避让、订阅更新隔离和设置持久化流程。本轮新增修复 1 项共享健康检查资源释放问题，复核并保留前轮 1 项 macOS 规则回退补丁。

没有操作正在运行的正式客户端，没有切换节点、断开连接或修改系统 DNS/代理。真实核心测试使用临时目录、随机回环端口并关闭 TUN；结果不是 Windows/Android 实机验收。

## 已修复问题

### P2：健康检查超时没有取消底层 HTTP 请求（三端共享）

触发：本地核心不返回 /version 响应头，或 /providers/rules 返回头后不结束正文。

原行为：Future.timeout 在两秒后返回失败，但底层请求仍挂起。后续检查可能累积未完成的连接、监听和等待任务，给已经异常的核心增加额外资源压力。没有证据将它认定为此前全局 UI 卡顿的根因。

修复：复用项目现有 HTTP 依赖的 AbortableRequest，在健康检查结束时取消该次请求；不关闭共享 API 客户端，不增加重试，不改变规则就绪条件和恢复阈值。版本接口禁用重定向，与规则接口一致。

回归：修复前两种挂起场景均失败；修复后验证超时确实发出取消、正文监听结束，并且同一客户端在接口恢复后能再次检查成功。

### P2：macOS 新规则缺失/为空未进入已有旧规则回退（前轮修复复核）

共享恢复分类器原先未识别 macOS 规则预处理的两种 TUN_RULE_FILES 错误。补充精确识别后，可恢复已确认旧规则并最多重试一次；权限错误、取消、不明确的读取错误不淘汰规则版本。Windows 没有该 macOS 专用错误的产生路径，不将共享文件改动等同于三端存在同一故障。

## 第二轮：订阅与日常操作持久化

本轮继续检查订阅刷新/来源保留、设置写入、后台初始化重试、更新下载取消和订阅文件持久化。新增两项可复现修复，均位于三端共享的 subscription_service_persistence.dart，没有修改三端网络或正在运行的客户端。

### P1：存储读取失败被误判为文件损坏

原实现将读取与解析包在同一个通用 catch 中。临时权限不可读时，subscriptions.json 或 subscription_cache.yaml 会被移入 .bad 备份，内存列表被清空；之后启动可能继续显示为空，而原数据并非损坏。

用真实临时文件 chmod 000 复现两种情况，修复前两项回归均失败。修复后 FileSystemException 向上返回，文件和已加载节点保留；恢复权限后重新加载成功。三端服务均通过 AsyncLazy 初始化，失败尝试不会被永久缓存。存储未恢复时仍可能初始化失败，不承诺绕过存储错误正常启动。

读取改为 readAsBytes 后显式 utf8.decode，使真实 I/O 失败和编码损坏可以区分。另有两项测试确认无效 UTF-8 仍会按损坏数据备份处理，既有破损 YAML、语义错误和超大缓存测试仍通过。

### P2：原子写入失败遗留临时订阅文件

原实现写入临时文件后若重命名失败，没有清理本次临时文件。多次重试可能积累完整订阅缓存，增加磁盘占用。

用临时目标目录制造替换失败，修复前测试捕获到遗留的 .tmp 文件。修复后 finally 清理本次临时文件，并保持目标路径内已有数据不变。没有清理历史用户文件或历史备份；也不能保证存储本身持续拒绝删除时一定清理成功。

## 第三轮：后台任务、测速和统计生命周期

换向审查首页流量采样、单节点/批量测速结果归属、节点切换、出口国家标记与账户数据轮询。新增修复一项三端共享的流量采样资源释放问题。

### P2：流量统计超时后仍保留底层连接

首页可见且连接时，统计面板在每次采样结束一秒后发起下一次采样。原读取函数仅对 Future 设置两秒超时，不取消 HTTP 请求，核心统计接口持续挂起时可能累积未完成请求。此次是前轮健康检查问题在另一条定时采样路径上的补充修复，不作为此前低配设备全局 UI 卡顿的根因结论。

改用现有 HTTP 依赖的 AbortableRequest，在请求结束时取消本次操作，不关闭共享客户端，不改变统计字段、刷新频率和显示效果。既有连接代次检查仍防止旧连接结果写入新连接。

两项新增回归使用随机本地端口的原始 TCP 服务，分别模拟不返回响应头、返回部分响应后挂起。修复前，在应用超时后等候一秒仍未收到 TCP 对端断开，两项测试失败。修复后直接观察到 TCP 断开，同一客户端随后可读取下一次有效统计，全部通过。

初版测试用 HttpServer.connectionsInfo().active 作为关闭判断，但服务端未完成响应可能仍计为活动请求，这不是可靠的 TCP 关闭证据。该初版导致修复后仍失败，已改为原始 Socket 的 onDone/onError 事件并重新做修复前/后对照；没有通过放宽超时或删掉关闭断言获得通过。首轮日志保留为验证方法修正记录，不将其作为新的产品故障。

## 第四轮：实际节点状态与异步操作交接

本轮检查节点选择、连接/断开后的迟到结果、规则重载失败反馈、离线选择持久化和快捷连接配置失效流程。新增一项三端共享修复。

### P2：全局选择未知时误报 PROXY 组节点

原 currentSelectedProxyName 在全局模式读取 GLOBAL 失败或返回空值时，会回退返回 PROXY 组节点。但 GLOBAL 可能实际选择另一个节点或直连，因此不能将 PROXY 的选择当成已确认的当前节点。规则模式也可能直接返回 DIRECT、PASS 等内置策略名。

修复后按当前模式读取对应组，仅当 GLOBAL 明确指向 PROXY 时继续查询 PROXY。空值、读取失败和内置策略均返回未知，不猜测节点。出口节点归属复用同一判断，同时保留手动直连覆盖时不能归属代理节点的保护。没有增加主动断开、重试或修改分流策略。

两项新增回归使用本地模拟核心 HTTP 服务：GLOBAL 返回 503、空字符串、内置策略时不得误用 PROXY 节点；恢复有效 GLOBAL 节点或明确指向 PROXY 后正常读取。另验证规则模式下内置策略不会作为节点名返回。修复前两项失败，修复后通过。

## 第五轮：设置读取、初始化重试与更新中断

### P1：设置读取失败被当作内容损坏，可能丢失用户设置

三端 SettingsService 原来将文件读取和 JSON 解析放在同一个通用 catch 中。临时读取失败后，Android 可能直接用默认值覆盖原文件，桌面端可能将原文件按损坏内容处理并重建默认值，影响用户端口、主题和手动规则。此问题是前轮订阅持久化错误分类在设置服务中的另一处独立路径。

修复以 readAsBytes 后显式 utf8.decode 区分真实文件 I/O 错误与编码损坏。FileSystemException 直接上抛，保留原文件；真正的无效 UTF-8、JSON 和设置字段仍进入既有损坏恢复流程。没有增加新的存储层，也没有改变正常写入、密钥迁移和连接策略。

每端新增两项测试，共六项：读取失败保留原文件、恢复后加载原端口；无效 UTF-8 仍恢复默认设置并保留已有密钥。Android 和 Windows 服务使用本机真实临时文件 chmod 000 模拟不可读，Windows 原生和 root 环境跳过此 POSIX 模拟。macOS 会预先归一化权限，因此使用限定于目标文件读取方法的故障注入，保留真实文件类型检查和正常文件操作；断言明确匹配注入错误，避免将前置权限错误误当作读取路径已通过。三端最终有效的修复前回归均失败，修复后均通过。
